# Private file storage

## Current choice

No database is necessary for this small exchange. Cloudflare authenticates people; our configuration maps email to participant ID. Two private files hold the persistent data:

- `config/family.private.json`: event details, participant IDs, display names, and exact Google-account emails. The prepared ignored private config contains the family names and placeholder Gmail addresses; replace those emails before deployment. The committed example contains fictional people only. Fresh checkouts can copy it and enter their private family details.
- `config/draw.private.json`: event ID and giver-to-recipient ID mapping, created automatically during server initialization when absent, and reused on later starts. The manual `npm run draw -- config/family.private.json config/draw.private.json` command is optional.

Both paths are configurable at runtime and relative to the server working directory unless absolute. Both files are excluded from Git at these default paths. Custom paths must be kept private and explicitly excluded too. Never put them under `static/` or a public document root.

## Container mount

See the runnable [Compose example](../compose.yaml) and [deployment instructions](../README.md#docker-deployment), including host UID/GID permissions.

Family configuration and saved draws live together in `config/`. Mount that directory once, writable by the server user so startup can create a missing draw. For a container whose app directory is `/app`, the Compose settings are:

```yaml
volumes:
  - ./config:/app/config
environment:
  FAMILY_CONFIG_PATH: /app/config/family.private.json
  DRAW_PATH: /app/config/draw.private.json
```

Finalize the family configuration before starting the container. The server initialization hook creates a missing draw before responding to requests; builds skip this step. It prints no pairings. Existing draws are only read and validated. For private-family local development, use `DEV_DRAW_PATH=config/draw.dev.private.json`; keep this separate from the production draw in the same directory. Back up the whole directory together.

## Guarantees and limitations

Startup and the optional organizer command validate config, generates a uniformly shuffled draw rejecting self assignments and configured directional exclusions, and publishes a complete file atomically without replacing an existing draw. The draw file is created with owner-only permissions; a newly created storage directory is owner-only. Keep the configuration owner-readable only as well, for example `chmod 600 config/family.private.json`.

After initialization, the app only reads: no writes on reveal, no redraw on refresh or restart while the draw exists, and no mutable sessions or counters to coordinate. Every reveal loads and validates the saved draw, and looks up the giver using only authenticated email. Only the recipient's display name is returned. Invalid configuration, an unreadable/corrupt existing draw, a changed event or participant IDs, self assignment, forbidden pairing, duplicate recipient, or duplicate ID/email fails closed. Only an absent draw permits generation, and only during initialization. A draw removed while running is not regenerated by reveal requests.

The application cannot detect a deliberate edit that replaces the draw with another valid permutation. Treat files and backups as organizer-controlled secrets. Keep the same event and participant IDs for an existing draw; generate a new event for next year. Directional exclusions are configured in the `exclusions` array using `{ "giver": "alex", "recipient": "jamie" }` entries; list both directions to exclude a pair mutually. Unknown participant IDs in rules are rejected. Generation stops after 10,000 unsuccessful attempts without saving a draw if rules are impossible or too restrictive. Previous-year restrictions are not implemented.

Back up config and draw together, retain the same private volume/path across deployments, and restore the existing draw after a machine replacement. Restore backups before starting: if the draw is absent, initialization creates a new one. For multiple Node instances, use the same persistent directory; atomic no-overwrite publication handles simultaneous starts, and each instance validates the winning saved draw. Independent directories can produce different draws. Avoid concurrent organizer changes; publish updates deliberately and validate them before restarting.

## When to add a database

Use durable database storage when adding writable wishlists, organizer editing, invitations, reveal audit/history, multiple independently managed events, or mutable state shared across instances. SQLite suits a single persistent Node host; Cloudflare D1 is a candidate if moving to Workers. A local/ephemeral serverless filesystem is not a persistence strategy. The current Node filesystem imports must be replaced before deploying to Workers.

## Development data

`DEV_AUTH_ENABLED=true` bypasses Cloudflare only in loopback SvelteKit dev mode. `DEV_FAMILY_SOURCE=fictional` uses the committed fictional config and fixed example draw. `DEV_FAMILY_SOURCE=private` reads `FAMILY_CONFIG_PATH`, with a separate saved `DEV_DRAW_PATH` created at initialization when absent. The development draw is ignored by Git and never falls back to `DRAW_PATH`. Production ignores these development settings and uses only private files and verified Cloudflare identity.
